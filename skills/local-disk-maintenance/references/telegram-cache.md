# Telegram 缓存：完成文件、硬链接与下载片段

用户选择“保留自动下载，只清理缓存”时，保持自动下载开关和额度。
缓存可能继续增长；报告清理时点的实际容量，不承诺此后一直保持目标余量。

## 优先应用内清理

在 Telegram 的设置 → 数据与存储 → 存储使用量中检查可清缓存，然后只执行
本轮已授权的清理。先取得真实窗口状态；快捷键或点击超时后重新读状态，
不能盲目重复点击。聊天记录、帐号数据库和其他应用的数据不属于媒体缓存。
界面清理成功与系统容量实测分别留证；未取得原生回读时不能声称界面清理成功。
Windows 采用该平台的应用内入口，不照搬 Mac 容器路径或 APFS 检查。

## Mac 文件级替代路径的已验证边界

本机原生 Telegram 的 MediaBox 中，完成文件与同名 `_partial` 可以是同一
device/inode 的两个硬链接，另有 `_partial.meta`。按路径相加会重复计数；
只删除其中一条路径通常不释放内容块。普通 `agent-disk plan --kind cache`
有意排除多硬链接文件，不能把此经验解释成允许去掉该检查或直接删整个 media。

确需文件级替代时，先在当次状态下制定独立的组清单并审阅执行器：

1. 根目录由本机当前帐号配置确认；限定已验证命名的云文档完成文件。
   完成文件必须存在，配对 partial 的 device/inode/size 必须一致。
2. 对组内每个 inode，清单内路径数须等于系统 nlink；有组外硬链接就保留。
   按 inode 去重核算分配量和私有量，不按三条路径叠加。
3. 核全部组成员的完整 SHA、身份、冷却期和活动句柄；执行前再检查。
   外部链接、内容变化、活动句柄、仅有 partial、不同 inode 的 partial、
   匿名临时目录及聊天数据库均不进入这个完成缓存规则。
4. 固定一次原尝试，保留 INTENT/RESULT。删除前持续核身份和预期链接计数；
   中途有变化即停止，不自动重放。只有全部路径确认消失、全部链接已解除且
   本方文件句柄已关闭，才登记该组的回收观察；全卷空间仍独立实测。

执行器的验证需覆盖真实硬链接组、组外链接、独立 partial、内容变化、打开句柄
和中途失败。不要直接复用上次的帐号路径、inode、plan 或已结束的执行目录。

2026-11-02 的 Mac 实例：46组、138路径，按 inode 去重的删除前私有量
830,611,456B。它证明这个有限完成缓存范围的处理结果，不证明任意 partial
均可删，也不证明所有 Telegram 版本都使用同一布局。对应原始操作回执保留
在本机任务目录，不随 skill 发布帐号标识或缓存内容。
